## Staff reply implementation checkpoint

**FR-018 staff reply from a claimed handoff.** The staff composer calls `POST /v1/staff/conversations/:id/messages` with the current conversation version and an idempotency key. The transaction checks current tenant/location access and handoff assignment, encrypts and attributes the outbound message, and queues the existing channel event with the state change and audit. The browser preserves the original key and version for retrying an uncertain submission. The API reports that the reply was queued.

Retain the [HTTP](../../apps/api/tests/staff-conversation-queries.test.ts) and [workspace](../../apps/web/src/lib/staff-workflow.test.ts) regressions. On 19 November 2026, all 17 [staff-operations tests](../../tests/database/staff-private-operations.test-suite.ts) passed on a disposable PostgreSQL 17.12 database. The staff reply test proved unauthorized use is rejected, a failed outbox write rolls back the reply, a concurrent replay queues one encrypted and attributed message, and the next inbound message returns the conversation to `awaiting_staff` with staff mode intact. The focused run used `vitest run tests/database/s4a-schema.test.ts -t "S17 real PostgreSQL private operations"` against that local instance. Deployed delivery, assignment/reassignment and the other [S22 gates](s22-completion-checklist.md#open-gates--no-invented-completion-percentage) remain open.
